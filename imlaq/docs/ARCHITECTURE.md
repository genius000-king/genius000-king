# بنية المشروع

## الفكرة في سطرين

النموذج ما يدخل الرام كله. الجزء اللي يشتغل مع **كل** توكن يبقى في الرام، والباقي يُقرأ من التخزين **وقت الحاجة**، وجزء من الرام محجوز للجوال دائمًا عشان ما يعلّق.

هذا ينجح فعليًا مع نماذج **MoE**، لأن كل توكن يشغّل كم خبير بس من مئات. مع النماذج الكثيفة (Dense) يشتغل بعد، بس كل توكن يقرأ كل الجزء اللي برا الرام.

```
السرعة ≈ سرعة قراءة التخزين ÷ البايتات اللي تنقرا من التخزين لكل توكن
```

## الطبقات

```
┌──────────────────────────────────────────────────────────────┐
│ app                 الواجهة (Compose) · ViewModels · الربط    │
├──────────────────────────────────────────────────────────────┤
│ core:designsystem   الثيم والمكوّنات (فحمي · كريمي · زجاجي)   │
├───────────────┬───────────────┬───────────────┬──────────────┤
│ core:device   │ core:memory   │ core:models   │ engine:host  │
│ فحص الجهاز    │ مخطط الذاكرة  │ قارئ GGUF     │ تشغيل المحركات│
│ مراقب الضغط   │ (منطق صافي)   │ متنبئ السرعة  │ كعمليات منفصلة│
├───────────────┴───────────────┴───────────────┼──────────────┤
│ core:common (Bytes)                           │ engine:api   │
│                                               │ عقود المحركات │
│                                               │ + البروتوكول  │
├───────────────────────────────────────────────┴──────────────┤
│ native (C++) — كل محرك ملف تنفيذي مستقل داخل الـ APK          │
│ libimlaq_text.so  = bmoe-cli (BigMoeOnEdge + llama.cpp)      │
│ libimlaq_stt.so   = whisper.cpp            (المرحلة 3)       │
│ libimlaq_tts.so   = sherpa-onnx            (المرحلة 3)       │
│ libimlaq_image.so = stable-diffusion.cpp   (المرحلة 4)       │
└──────────────────────────────────────────────────────────────┘
```

| الوحدة | نوعها | مسؤوليتها |
|---|---|---|
| `core:common` | Kotlin صافي | `Bytes`: كل حجم في التطبيق يمر من هنا عشان ما تختلط الوحدات |
| `core:memory` | Kotlin صافي | `MemoryPlanner`: يوزّع ميزانية الرام بين المحركات حسب الأولوية |
| `core:device` | Android | `DeviceProfiler` (رام، أنوية، معالج، حرارة، تخزين) و`MemoryWatcher` (ضغط الذاكرة) |
| `core:models` | Android | `GgufReader` و`ModelSummary` (خبراء أو كثيف) و`SpeedEstimator` و`ModelStore` |
| `core:designsystem` | Compose | الثيم والخط والمكوّنات. الشاشات ما تكتب لونًا بيدها أبدًا |
| `engine:api` | Kotlin صافي | واجهة لكل نوع: نص، صوت لنص، نص لصوت، صور. ومحلّل البروتوكول |
| `engine:host` | Android | `RunnerProcess` و`MoeTextEngine` و`EngineService` |
| `app` | Android | الشاشات والربط (`AppContainer`) |

**القاعدة:** المنطق اللي يحتاج اختبار (المخطط، القارئ، البروتوكول، المتنبئ) يعيش في كود صافي بدون Android، ومختبر على الـ JVM.

## القرارات وأسبابها

### ١. كل محرك عملية (process) مستقلة، مو JNI
أخذناه من BigMoeOnEdge لأنه أصح لتطبيقنا بالذات:
- **العزل:** لو المحرك انهار (segfault)، يموت المحرك والتطبيق يبقى.
- **ما فيه تعارض رموز:** llama.cpp وwhisper.cpp وstable-diffusion.cpp كل واحد يجيب نسخته من ggml. في عمليات منفصلة ما يتصادمون.
- **الذاكرة ترجع فورًا:** إيقاف العملية يرجّع كل بايت للنظام، وهذا اللي يحتاجه مخطط الذاكرة لما يطرد محركًا.

التواصل يكون JSON سطر بسطر عبر stdin/stdout (`docs/PROTOCOL.md`).

### ٢. نبني على BigMoeOnEdge، ما نعيد اختراعه
`third_party/bigmoeonedge` (Apache-2.0) فيه استريمنج الخبراء من الفلاش: O_DIRECT، كاش LRU، قراءة متوازية، تداخل القراءة مع الحساب، وprefill على NPU سنابدراقون. نستخدمه كما هو من submodule مثبّت على commit محدد، ونحدّثه بقرار.

### ٣. مخطط ذاكرة واحد لكل المحركات
BigMoeOnEdge يدير كاش نموذج واحد. احنا عندنا نص وصوت وصور ممكن تشتغل مع بعض، فـ `MemoryPlanner` يوزّع على مرحلتين:
1. كل محرك ياخذ **حدّه الأدنى** حسب الأولوية (الأمامي ← المساعد ← الخامل). الأقل أولوية يُطرد وما يزاحم الأعلى.
2. الباقي يتوزّع **كاش** إلى حد ما يفيد.

الميزانية = (المتاح + اللي تستخدمه محركاتنا) − المحجوز للجوال، وتصغر مع ضغط الذاكرة.

### ٤. ضغط الذاكرة بالمراقبة الدورية، مو onTrimMemory
من Android 14 ما يوصل `TRIM_MEMORY_RUNNING_*` للتطبيق الأمامي، وهي بالضبط المستويات اللي تهمنا وقت التوليد. لذلك `MemoryWatcher` يقرأ الحالة كل ثانيتين، ويستخدم PSI (`/proc/pressure/memory`) لو النظام يسمح.

### ٥. النماذج في التخزين الداخلي للتطبيق
`filesDir/models` نظام ملفات حقيقي (f2fs/ext4)، فـ O_DIRECT يشتغل بكامل السرعة. مسار `/sdcard` يمر عبر FUSE. العيب: حذف التطبيق يحذف النماذج، وعشان كذا في المرحلة 2 نضيف تصدير واستيراد.

### ٦. القراءة فقط، بدون swap
الأوزان تُقرأ من الفلاش وما تنكتب أبدًا. الكتابة هي اللي تستهلك الـ NAND، والقراءة تكاد ما تأثر. فكرة "swap على التخزين" كانت بتأكل الذاكرة الفلاش بسرعة.

### ٧. `android:appCategory="game"`
بعض الشركات (مثل OxygenOS) ترفع سقف تردد المعالج للتطبيقات المصنّفة ألعاب. BigMoeOnEdge قاس الفرق بنفسه. التوليد أثقل شي يسويه الجوال بعد الألعاب.

## مسار طلب نصي

```
الواجهة → TextEngine.generate(request)
        → MoeTextEngine: {"cmd":"generate",...} على stdin
        → bmoe-cli: يوجّه كل توكن، يقرأ الخبراء الناقصة من الفلاش، يحسب
        ← BMOE_PROGRESS {delta_text, io_ms, cache_hit_pct, ...}   (لكل توكن)
        ← BMOE_DONE {text, tok_s, ...}
        → TextEvent.Delta / Telemetry / Finished → الواجهة
```
