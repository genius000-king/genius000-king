# TV Control Hub — المعمارية والقرارات التقنية

> الحالة: مسودة معتمدة للتنفيذ. كل رقم أداء هنا **هدف** يُعدَّل بعد القياس على الجهاز الفعلي، وليس وعدًا.

## 1. ما الذي يمكن وما الذي لا يمكن (قيود صلبة)

هذه القيود تحدد الهندسة كلها، ولا يحلها الكود:

| القيد | الحقيقة | التبعة على التصميم |
|---|---|---|
| الجهاز | Xiaomi TV Box S 3rd Gen: 2GB RAM و32GB تخزين، نظام **Google TV** (ليس Android TV الخام)، معالج رباعي حتى 2.5GHz، GPU من فئة Mali G310 | الميزانية الصغيرة تمنع تضمين Node/Python أو Netty، وتفرض قياس المشفّر العتادي أولًا |
| التقاط الشاشة | MediaProjection يطلب موافقة **لكل جلسة**؛ على Android 14+ الـ token يُستخدم مرة واحدة فقط | جلسة الالتقاط تعيش طوال عمر خدمة التلفزيون، ويتصل العملاء بها ويفصلون عنها بلا طلب إذن جديد |
| حقن الإدخال | لا يوجد API عام يحقن أزرار D-pad أو Volume بدون صلاحيات النظام أو shell | الريموت الكامل بأزرار الاتجاهات يحتاج مسارًا اختياريًا (Shell Bridge) — انظر D5 |
| قراءة GPU | لا يوجد API عام لنسبة استخدام GPU | نعرض هوية الـ GPU وإصدار OpenGL/Vulkan فقط، لا "نسبة الاستخدام" |
| الحرارة | `PowerManager.getCurrentThermalStatus()` يعطي **حالة** (none…shutdown)، ودرجة الحرارة الفعلية تتطلب صلاحية نظام | نعرض الحالة الحرارية، لا درجة مئوية |
| المحتوى المحمي | FLAG_SECURE و DRM يعطيان شاشة سوداء في الالتقاط | نعرض للمستخدم سبب السواد، ولا نحاول تجاوز الحماية |
| Node/Python | لا يُشغَّلان داخل التطبيق بدون runtime؛ Termux مسار محتمل لكنه غير مؤكد على التلفزيون | الخدمات عبر Termux اختياريًا، ومع allowlist؛ لا shell حر من الجوال |

## 3. خريطة الوحدات

المبدأ: **كل محرك = ثلاثة أجزاء منفصلة**.
- `api`: منطق نقي وواجهات وعقود. وحدة JVM بلا أي تبعية Android، فلا يستطيع أن يستورد Android أصلًا (يُفرض بالبناء نفسه).
- `tv` / `mobile` / `android`: التنفيذ الخاص بالجهاز. يعتمد على `api` فقط.
- `ui` (داخل الجوال أو التلفزيون): شاشات تستهلك واجهات `api` فقط.

```
tv-control-hub/
├─ apps/
│  └─ hub/                    تطبيق واحد للجوال والتلفزيون: MainActivity تختار الواجهة حسب الجهاز
│     ├─ mobile/              واجهة الجوال (الملاحة + الشاشات)
│     └─ tv/                  واجهة التلفزيون (الشاشات الست + خدمة Foreground)
├─ core/
│  ├─ common/                 JVM — Result, AppError, منافذ الساعة والسجل
│  ├─ protocol/               JVM — عقود الرسائل، الإصدارات، الترميز، الرسائل المجهولة
│  ├─ design/                 Android — tokens الهوية، Theme فاتح/داكن، مكونات زجاجية
│  └─ testing/                JVM — Fakes ومساعدات الاختبار
├─ engines/
│  ├─ pairing/   api · android          (P2)
│  ├─ transport/ api · tv · mobile      (P2)
│  ├─ stream/    api · tv · mobile      (P1)
│  ├─ input/     api · tv · mobile      (P1 للنقر والأزرار، P3 للريموت الكامل)
│  ├─ monitor/   api · tv · mobile      (P4)
│  ├─ files/     api · tv · mobile      (P5)
│  └─ services/  api · tv               (P6)
└─ build-logic/                         Convention plugins لكل الوحدات
```

### قواعد الاعتماد (تُفرض بالبناء والاختبار)
1. `api` لا يعتمد إلا على `core:common` و`core:protocol`. وهو JVM، فلا يصل إلى Android.
2. `tv` و`mobile` داخل المحرك الواحد لا يعتمد أحدهما على الآخر، ولا يعتمد محرك على تنفيذ محرك آخر. التواصل بين المحركات عبر `api` فقط.
3. `core:protocol` هو العقد الوحيد المشترك بين التلفزيون والجوال. لا يُشارَك أي نوع آخر بين التطبيقين.
4. تطبيقات `apps/*` هي الوحيدة التي تعرف كل التنفيذات (DI)، وهي فقط تربط الوحدات ببعضها.
5. المكونات تستهلك `api` فقط. الشاشة لا تعرف كيف يُنفَّذ البث.
6. لا وحدة فارغة: الوحدة تُنشأ عند تنفيذ ميزتها، وتُوثّق هنا قبل ذلك.

## 4. الاتصال والتدفق

```
الجوال                                          التلفزيون
 ├─ اكتشاف (NSD: _tvhub._tcp)  ──────────────▶ إعلان NSD + TXT(version, id, port)
 ├─ إقران (QR أو SAS)           ══TLS مثبَّت══▶ موافقة يدوية على شاشة التلفزيون
 ├─ Control WS (protocol)       ══TLS══════▶ الصلاحيات تُفحص لكل رسالة
 │     ├─ إشارات WebRTC (SDP/ICE) ─────────▶ PeerConnection
 │     └─ أوامر: input / monitor / files / services
 └─ WebRTC media ◀═══════ DTLS-SRTP ════════ ScreenCapturer → H.264 (عتادي إن وُجد)
```

- **جلسة الالتقاط واحدة لكل تشغيل للخدمة**: تُنشأ بعد موافقة واحدة، ويُعاد استخدام الـ `VideoTrack` لكل عميل جديد. لا `stop/start` بين العملاء لأن الـ token لا يتكرر.
- **ICE**: مرشحات LAN فقط في الإصدار الأول. لا STUN/TURN قبل تنفيذ النقل عن بُعد.
- **حالات الاتصال**: `Discovering → Pairing → Connected → Streaming` مع `Reconnecting` (backoff أُسّي 0.5s إلى 30s مع jitter) و`Revoked` (إغلاق فوري).

## 5. الأمان

- **الهوية**: مفتاح EC P-256 لكل جهاز. على الجوال يُحفظ في Android Keystore، وعلى التلفزيون كذلك. المفتاح الخاص لا يغادر الجهاز.
- **TLS**: شهادة ذاتية التوقيع على التلفزيون (EC P-256)، ويُثبَّت SHA-256 لـ SPKI في QR وفي قائمة الأجهزة الموثوقة. لا `ws://` في الإصدار النهائي.
- **الإقران**: QR يحمل `{hosts, port, spkiPin, pairingSecret(256-bit), expiresAt}`، صلاحيته دقيقتان ويُستهلك مرة واحدة. ولأن السر لا يمر عبر الشبكة، لا حاجة لـ PAKE. التلفزيون يطلب "سماح" يدويًا على الريموت.
- **الرمز اليدوي (بدون كاميرا)**: SAS من 6 أرقام مشتق من `HKDF(ECDH(pubA, pubB), transcript)`؛ يقارنه الشخص على الشاشتين. MITM يصيب فقط باحتمال 10⁻⁶ لكل محاولة، ولا يُخمَّن أوفلاين لأن الـ SAS لا يكشف سرًا.
- **حدود المحاولات**: 5 محاولات إقران في الدقيقة، وقفل 10 دقائق بعد 10 إخفاقات.
- **الصلاحيات** لكل جهاز مقترن: `screen.view`، `input.control`، `files.read`، `files.write`، `services.manage`، `system.info`. تُفحص **في الخادم** لكل رسالة، لا في الواجهة فقط.
- **الإلغاء**: إزالة الجهاز تُغلق جلساته فورًا وتحذف بصمته.
- **السجلات**: لا تُسجَّل أسرار أو tokens أو محتوى ملفات. تُحجب القيم الحساسة قبل الكتابة.
- **الملفات**: جذور مسموح بها فقط، تحقق `realpath` يرفض أي مسار يخرج منها، بما فيه الروابط الرمزية.
- **الخدمات**: أوامر مُعرَّفة بالاسم فقط، ومعاملاتها مُتحقق منها بنوع وطول وقائمة بيضاء. لا تُمرَّر سلاسل shell من الجوال مطلقًا.

## 6. تصميم الواجهة (UI/UX)

### المبادئ
- **Progressive Disclosure**: كل شاشة رئيسية فيها **4 إجراءات كحد أقصى**. الخيارات المتقدمة خلف "خيارات متقدمة" قابلة للطي، أو داخل صفحة فرعية.
- **صفحة لكل وظيفة**: لا تُخلط أداتان في شاشة واحدة. التنقل عبر قوائم بطاقات، وكل بطاقة تفتح صفحة مستقلة.
- **RTL أولًا**: العربية هي الاتجاه الأساسي، والإنجليزية LTR كاملة. كل أيقونة اتجاهية تُقلَب في RTL.
- **داكن وفاتح**: الداكن هو المرجع، والفاتح مشتق منه بالقيم الموثقة أدناه.
- **التلفزيون بالـ D-pad**: كل عنصر قابل للتركيز، والتركيز مرئي بحلقة واضحة. ممنوع الاعتماد على hover أو السحب في التلفزيون. النصوص ≥ 18sp.
- **لا نصوص طويلة**: كل بطاقة عنوان + سطر واحد، والتفاصيل داخل الصفحة.

| الرئيسية | حالة الاتصال · ملخص الجهاز (3 مؤشرات) · إجراءان سريعان: "الشاشة" و"الريموت" |
| التحكم | الشاشة المباشرة · الريموت · الماوس (Touchpad) · لوحة المفاتيح · الاختصارات |

| الإعدادات | الاتصال · الأمان · الصلاحيات · المظهر · الأجهزة المقترنة |

الرئيسية وحالة الاتصال · إقران الجوال (QR + رمز SAS) · الأجهزة الموثوقة · الأذونات · الخدمات النشطة · الإعدادات.

**الشكل**: نصف قطر البطاقات 16dp، والأشرطة 18dp. البلور 16dp للبطاقات و18dp للأشرطة على API 31+ فقط؛ وعند غيابه يُستخدم تعتيم `glassStrong`. **التلفزيون لا يستخدم البلور** (ميزانية GPU)، ويستخدم تعتيمًا ثابتًا.

**الخلفية** (من المرجع): قاعدة `#0A0A0A` + أربع هالات بيضاء ناعمة بعتامة 7% عند المواضع النسبية (0.15, 0.12) نصف قطر 0.45، و(0.85, 0.38) نصف قطر 0.40، و(0.30, 0.75) نصف قطر 0.45، و(0.80, 0.92) نصف قطر 0.35. الحبيبات (grain) على الجوال فقط.

**الخط**: المرجع يستخدم خطًا عربيًا هندسيًا. نستخدم بديلًا مفتوحًا بدعم عربي كامل، مرشح: **IBM Plex Sans Arabic** (OFL)، ويُتحقق بصريًا. المقاسات ليست موثقة في المرجع، فهي قرار تصميمي يُراجَع على الجهاز.

### ماذا لا نأخذه من المرجع
الشعار "عملاق" والاسم وعلامة الـ footer وأسماء النماذج الظاهرة في الصور. نشتق شعارًا مستقلًا لـ TV Control Hub.

## 9. أهداف الأداء (تُقاس وتُعدَّل في P1)

| المقياس | الهدف المبدئي |
|---|---|
| البث الافتراضي | 720p30، 2–4 Mbps |
| البث الاختياري | 1080p30، 4–6 Mbps، إذا أثبت المشفّر العتادي ذلك |
| الكمون glass-to-glass على LAN 5GHz | ≤ 150ms |
| ذاكرة التلفزيون (PSS) | ≤ 150MB في الخمول، ≤ 280MB أثناء البث |
| الجوال | لا إطارات مهدورة في القوائم (60fps) |
